# Memory Graph 双渲染架构升级：2D + Three.js 3D 完整开发指导

## 一、项目目标

请基于项目现有的 Memory Graph（记忆图 / 星图）实现进行渐进式架构升级。

本次升级的核心目标是：

1. 保留现有 2D 星图。
2. 新增真正的 Three.js 3D 星图。
3. 允许用户在 2D 和 3D 两种模式之间自由切换。
4. 完善记忆图和星图的画布平移、缩放和交互体验。
5. 实现真正的三维作用域轨道、中心星球和记忆星星。
6. 实现作用域、记忆星星之间的拖拽联动。
7. 实现用户布局持久化，避免每次重新进入页面都恢复默认位置。
8. 尽可能复用现有代码、业务逻辑、数据结构和依赖，避免不必要的重构。

**最重要的架构约束：不得用 Three.js 替换现有 2D 星图。必须同时保留 2D 和 3D 两种渲染模式。**

在开始修改之前，必须先完整检查现有源码、组件结构、状态管理、布局算法、样式、依赖、构建工具和测试。不要仅根据需求自行假设项目实现。

## 二、先理解现有项目，不要直接重写

现有项目采用 React.createElement + 原生 DOM 的方式构建界面。

现有 Memory Graph 主要实现特点：

- 使用 DOM 绝对定位星星节点。
- 使用内联 SVG 绘制节点之间的连线。
- `buildMemoryGraph()` 是纯函数，负责生成确定性布局。
- 布局包含黄金角螺旋和确定性斥力分簇。
- CSS 用于模拟远近纵深。
- 作用域簇包含 `scope、x、y、spread、orbit` 等数据。
- 节点使用二维 `x、y` 坐标。
- `z` 目前只是视觉深度比例，并不是真正的三维 Z 坐标。
- `GRAPH_METRICS` 管理现有布局参数。
- `graphLinkPath()` 负责生成二维 SVG 连线路径。
- `.graph-stage`、`.graph-zoomspace`、`.graph-canvas`、`.gnode` 是现有主要交互和渲染层。
- 当前 `graphZoom` 只有缩放，没有独立平移状态。
- 当前缩放主要围绕画布中心，不支持鼠标位置锚定缩放。
- `fitGraph()` 目前主要调整缩放。
- `graphNear` 负责搜索和邻域高亮。
- 记忆树和星图共享搜索、筛选、选中、悬停及详情抽屉状态。

请先确认这些信息是否仍然与当前源码一致。

### 必须遵守

1. 不要推翻现有 `buildMemoryGraph()`。
2. 不要删除现有确定性布局算法。
3. 不要把记忆树迁移到 Three.js。
4. 不要把整个 React 页面迁移到 Three.js。
5. 不要将所有逻辑堆进 `client.js`。
6. 不要手动修改构建输出目录中的生成文件。
7. 优先修改 `source/memory-panel/lib/` 下的源码。
8. 不要为了视觉效果破坏原有搜索、筛选、选择、详情抽屉等功能。

先完成源码检查，给出简短的现有架构分析和计划，再开始实施。除非发现会导致重大架构问题的缺失，不要停留在计划阶段，应继续执行。

## 三、整体架构：统一业务层 + 双渲染器

采用以下架构：

### 1. 统一业务数据层

统一管理：

- 记忆记录。
- 作用域。
- 节点之间的关联关系。
- 记忆节点 ID。
- 作用域 ID。
- 搜索和筛选结果。
- 当前选中节点。
- 当前悬停节点。
- 邻域高亮。
- 节点布局数据。
- 用户自定义位置。
- 视图切换状态。

2D 和 3D 必须消费同一套业务数据。

不允许 2D 和 3D 分别维护两份不兼容的记忆数据。

### 2. 2D 渲染器

继续使用现有：

- DOM。
- SVG。
- CSS。
- `buildMemoryGraph()`。
- `graphLinkPath()`。

负责二维星图的绘制和交互。

不需要 Three.js。

### 3. 3D 渲染器

新增独立 Three.js 模块。

负责：

- 真正的 3D 场景。
- 透视相机。
- 三维作用域球体。
- 三维轨道。
- 记忆星星。
- 三维连线。
- 光照和深度遮挡。
- 三维旋转。
- 三维节点拖拽。
- 三维空间布局。
- 动画和过渡。

### 4. React 业务层

React 继续负责：

- 页面结构。
- 工具栏。
- 2D / 3D 模式切换。
- 搜索。
- 筛选。
- 选中状态。
- 记忆详情。
- 业务状态同步。
- 组件生命周期。

Three.js 自己管理动画循环，不要在每一帧触发 React 全量渲染。

## 五、2D 和 3D 模式切换

在星图工具栏中增加 2D / 3D 切换入口。

用户可以随时切换。

### 2D 模式

- 使用现有 DOM + SVG。
- 使用二维坐标。
- 保留现有视觉风格。
- 支持平移和缩放。
- 支持节点拖动。
- 支持作用域拖动。

### 3D 模式

- 使用 Three.js。
- 使用真实三维坐标。
- 支持透视和深度遮挡。
- 支持三维旋转。
- 支持作用域、记忆节点拖拽。
- 支持动态联动。
- 支持独立的三维视角和相机状态。

### 切换要求

切换时：

1. 不重新请求或重建记忆业务数据。
2. 不丢失搜索和筛选条件。
3. 不丢失当前选中的记忆。
4. 不丢失用户保存的节点位置。
5. 不随机重新排列星星。
6. 尽可能保留当前视图中心和视觉焦点。
7. 两个渲染器不能同时产生重复的交互事件。
8. 切换时正确销毁或暂停非活动渲染器的动画和监听器。

两种模式分别保存自己的视图状态。

## 六、2D 画布平移与缩放

记忆图和 2D 星图都需要具备完整的画布交互能力。

### 1. 平移

支持：

- 鼠标左键拖动画布空白区域。
- 触控设备单指拖动（如果项目已有触控支持）。
- 拖动时画布跟随指针移动。
- 释放鼠标后停止。
- 不允许拖动星星时误触发画布平移。

使用 Pointer Events。

正确处理：

- pointerdown。
- pointermove。
- pointerup。
- pointercancel。
- pointer capture。
- 拖动距离阈值。

星星节点、按钮和交互控件应正确阻止事件冒泡。

### 2. 缩放

支持：

- Ctrl + 鼠标滚轮缩放。
- 触控板双指缩放（浏览器以 Ctrl + wheel 形式提供时）。
- 工具栏缩放按钮。
- Fit / 重置视图。

缩放范围必须明显大于当前范围，建议初始测试范围为：

- 最小缩放：0.08。
- 最大缩放：5。

这些数值应集中配置，方便调整。

### 3. 鼠标锚点缩放

缩放中心必须是鼠标当前所在位置，而不是始终围绕画布中心。

缩放前后，鼠标指向的画布内容应该保持在鼠标下方。

使用正确的坐标换算计算平移补偿。

### 4. Fit 视图

Fit 必须同时计算：

- 缩放比例。
- 水平平移。
- 垂直平移。

不能只修改 zoom。

Fit 应当将完整星图合理放入可视区域。

用户手动调整视图之后，不允许组件重新渲染时无故重新 Fit。

### 5. 状态隔离

记忆树、2D 星图、3D 星图分别保存视图状态。

不能让不同视图共用同一个 zoom 和 pan 状态，导致切换后视图互相覆盖。

## 七、真正的 Three.js 3D 星图

3D 模式必须使用真正的 Three.js 三维场景。

禁止仅使用 CSS 旋转、缩放或透视模拟 3D。

### 1. 场景结构

建议每个作用域对应一个独立 THREE.Group：

ScopeGroup
- CentralPlanet
- OrbitalRing
- MemoryStars
- MemoryConnections
- ScopeGlow

作用域整体拥有独立的：

- 世界坐标。
- 旋转。
- 缩放。
- 可见性。
- 用户自定义布局。

作用域内部的星星使用局部坐标。

### 2. 作用域中心星球

使用 SphereGeometry 创建真实球体。

要求：

- 具有真实的球体轮廓。
- 使用适度的材质和光照。
- 具有发光效果。
- 可以显示作用域名称。
- 可以作为作用域整体拖动的交互目标。
- 视觉上是当前作用域的中心。

不能只是一个始终朝向摄像机的圆形 DOM 元素。

### 3. 作用域轨道

使用 TorusGeometry 或适合的三维曲线创建真实轨道。

要求：

- 具有真实三维厚度或可见轮廓。
- 具有空间透视。
- 有前后遮挡关系。
- 可以绕中心旋转。
- 支持上下左右方向的旋转操作。
- 旋转时中心位置固定。
- 旋转不能让中心球体偏离轨道中心。
- 不同作用域的轨道可以拥有适度差异。

轨道旋转必须修改轨道或旋转容器的 rotation / quaternion，而不是直接修改轨道的位置。

旋转中心始终是作用域局部原点。

使用 Quaternion 处理复杂旋转，避免欧拉角组合导致异常。

合理限制翻转角度，避免轨道突然倒置。

### 4. 记忆星星

每条记忆记录对应一个三维节点。

要求：

- 每个节点具有稳定 ID。
- 使用真正的三维坐标。
- 根据重要性、类型或现有业务规则设置适当的尺寸和视觉效果。
- 具有深度遮挡。
- 可以被 Raycaster 精确拾取。
- 可以拖动。
- 可以显示名称或悬停信息。
- 可以选中并打开现有详情抽屉。
- 搜索结果和邻域高亮逻辑保持一致。

大量节点时使用 InstancedMesh 等优化方式，避免每个星星都创建大量独立 Mesh。

### 5. 记忆连线

使用 BufferGeometry 或合适的线段实现。

要求：

- 保留现有记忆关系。
- 支持关联高亮。
- 支持选中和搜索高亮。
- 节点移动后实时更新相关连线。
- 避免每帧创建大量新的 Geometry。
- 合理处理透明度和深度遮挡。

### 6. 标签

节点名称、作用域名称等文字应清晰可读。

可以使用：

- HTML overlay。
- CSS2DRenderer。
- Sprite。

根据性能和视觉效果选择。

文字不能因为摄像机旋转而变得无法辨认。

远距离节点可以适度隐藏次要标签，防止画面过于拥挤。

### 7. 光照与效果

建议使用：

- AmbientLight。
- DirectionalLight 或 PointLight。
- MeshStandardMaterial。
- 适量的发光材质。
- 可选 Bloom。

注意控制后处理开销，不要让所有节点都产生高成本光晕。

整体保持当前星图的深色宇宙视觉风格，但必须保证信息可读性。

## 八、3D 交互规则

所有交互必须有明确的手势映射，不能让同一个手势同时承担多个互相冲突的行为。

建议采用以下规则：

| 操作 | 行为 |
|---|---|
| 左键拖动空白画布 | 平移整个星图 |
| Space + 左键拖动空白画布 | 旋转整体 3D 视角 |
| 左键拖动作用域轨道 | 旋转当前作用域 |
| 左键拖动中心球体 | 移动整个作用域 |
| 左键拖动记忆星星 | 移动该记忆节点 |
| Ctrl + 滚轮 | 缩放视图 |
| 双击记忆星星 | 聚焦该记忆 |
| 单击记忆星星 | 选中并显示详情 |

如项目现有交互存在冲突，可以适当调整，但必须在最终实现中明确区分。

### 1. 轨道拖动

拖动轨道时：

- 只旋转当前作用域的轨道或对应旋转容器。
- 中心球体保持在原点。
- 作用域整体中心不移动。
- 轨道内的记忆节点根据父子层级正确联动。
- 旋转过程平滑。
- 松开后可以有适度惯性和减速效果。

### 2. 中心球体拖动

拖动中心球体时：

- 移动整个作用域 Group。
- 作用域内的轨道、星星、连线和标签一起移动。
- 其他作用域不应被直接移动。
- 与该作用域相关的跨作用域关系连线应正确更新。

### 3. 记忆星星拖动

拖动单条记忆时：

- 只移动目标记忆节点。
- 更新其相关连线。
- 相邻星星受到适度影响。
- 相关节点产生平滑的空间联动。
- 其他不相关作用域不应无故重新排列。

### 4. 空间拾取和拖动计算

使用 THREE.Raycaster 进行拾取。

将屏幕指针位置转换为 NDC 坐标。

将射线与合适的三维拖动平面求交，再将交点转换为对应父 Group 的局部坐标。

禁止直接将屏幕像素坐标赋值给三维世界坐标。

需要正确处理：

- 摄像机变化。
- 作用域旋转。
- 父子坐标转换。
- 深度变化。
- 拖动期间的连线更新。

## 九、三维动态布局与节点联动

推荐使用 d3-force-3d。

先确认当前项目兼容的版本及 API，再决定具体调用方式。

建议每个作用域使用独立的模拟系统。

可采用：

- 节点排斥力。
- 节点碰撞力。
- 关联吸引力。
- 中心约束力。
- 速度衰减。
- 空间边界约束。

### 拖拽联动要求

当用户拖动一颗记忆星星：

1. 目标节点跟随鼠标。
2. 相关节点受到一定影响。
3. 节点之间不能严重重叠。
4. 连线实时更新。
5. 其他节点平滑调整。
6. 松开后逐渐稳定。
7. 不允许整个星图突然随机重排。

拖动期间可以使用 fx、fy、fz 固定目标节点，释放后再恢复模拟。

### 关键约束

必须保留现有确定性初始布局。

动态布局只能作为用户交互之后的局部响应机制，不能每次刷新都重新随机生成节点位置。

模拟应设置合理的迭代次数、停止条件和性能限制。

当节点稳定后停止或降低模拟频率，避免持续消耗 CPU。

## 十、布局持久化

这是本次升级的核心要求之一。

用户手动调整过的位置必须保存。

优先复用项目现有的数据持久化方式，不要未经检查就直接假设使用 localStorage。

如果项目没有合适的布局持久化机制，再选择适合项目架构的存储方式。

建议统一的数据模型：

{
  version: 1,

  scopes: {
    "scope-id": {
      x: 0,
      y: 0,
      z: 0,
      rotationX: 0,
      rotationY: 0,
      rotationZ: 0
    }
  },

  records: {
    "memory-id": {
      x: 100,
      y: 50,
      z: 20
    }
  },

  views: {
    "2d": {
      zoom: 1,
      panX: 0,
      panY: 0
    },

    "3d": {
      cameraPosition: [0, 0, 500],
      cameraTarget: [0, 0, 0],
      zoom: 1
    }
  }
}

以上为建议结构，必须根据现有项目数据模型调整。

### 持久化规则

1. 使用稳定的记忆 ID 和作用域 ID。
2. 保存用户调整过的节点位置。
3. 保存作用域位置和旋转角度。
4. 保存 2D 平移和缩放。
5. 保存 3D 相机位置、目标点和视图状态。
6. 不能依赖数组下标作为节点身份。
7. 新增记忆不能导致旧记忆重新排列。
8. 删除一条记忆不能导致其他记忆重新排列。
9. 搜索和筛选不能删除被隐藏节点的布局。
10. 切换 2D / 3D 不得清空用户布局。
11. 需要提供恢复默认布局的入口。
12. 设计 schema version，支持未来迁移。

如果用户恢复默认布局，只清除用户自定义布局覆盖层，再使用默认确定性布局重新生成。

## 十一、性能和资源管理

Three.js 必须有明确的生命周期管理。

### 性能要求

- 使用独立 requestAnimationFrame 渲染循环。
- 不要每帧触发 React setState。
- 大量节点使用 InstancedMesh。
- 连线使用可复用 BufferGeometry。
- 避免反复创建和销毁 Material。
- 避免重复创建纹理和几何体。
- 合理使用像素比，控制高分辨率设备的 GPU 开销。
- 根据节点数量调整渲染策略。
- 页面不可见时暂停或降低渲染频率。
- 非活动模式不应持续运行昂贵的渲染循环。

### 资源清理

组件卸载或模式切换时：

- 停止动画循环。
- 移除事件监听。
- 释放 Geometry。
- 释放 Material。
- 释放 Texture。
- 释放 WebGLRenderer。
- 清理 ResizeObserver。
- 清理模拟系统。
- 释放 DOM 容器。
- 避免重复初始化导致多个 canvas 叠加。
